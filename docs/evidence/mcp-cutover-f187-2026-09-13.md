# F187 (F150b2) — the connector is a binary now, and mcp-worker.mjs is deleted (2026-09-13)

Spec 129 and spec 065, KI-100. F184 captured the surface, F185 ported the calls; this is the
cutover and the deletion.

## The question the row was filed on, and its answer

`mcp.mjs` spawns the tool worker named by `runtime.toolWorker`, and the supervisor **probes a
candidate** before adopting it and bumping `connectorGeneration`. Both assumed the tool layer was a
JS file that could be swapped at runtime, so the row asked what *"update the connector layer"* means
once that layer is a compiled binary.

**The contract does not change; the payload does.** Reading the supervisor settles it: a connector
update never staged an artifact — it re-probed the worker *at its published path* and, if the probe
passed, bumped the generation so every facade replaced its child on the next request. The new code
came from the checkout itself. For a binary that is one step longer, and it is a step the **desktop
layer already takes**: build, then probe, then adopt.

So:

- `red-mcp` is the connector, resolved as `$RENGINE_RED_MCP` → release → debug, and published in
  the descriptor so a facade runs the binary the supervisor probed.
- The connector layer **builds** (`cargo build -p red-mcp`) before probing. The JS file changed as
  soon as the checkout did; a binary does not, and a layer that probed a stale build would report
  success for code nobody was running.
- The probe is the binary's own `--probe`: it asks the three questions `runtime/tools.mjs` asked
  over MCP — does it start, does it carry `workspace_info`, `update_status` and `update_workspace`,
  does it answer bound to this root — and says so by exiting 0.
- Everything else in spec 065 is untouched: completion stays distinct from acceptance, the
  generation is what makes facades replace their worker, and a pane's MCP is still spawned per
  launch.

## What was deleted, and what replaced each part

| deleted | replaced by |
| --- | --- |
| `agents/mcp-worker.mjs` (304 lines) | `red/red-mcp` — the surface (F184) and the calls (F185) |
| `orchestrator/runtime/tools.mjs` (25 lines) | `red-mcp --probe`, run by the supervisor |

`agents/mcp.mjs` stays: it is the facade that keeps a pane's connection alive across a connector
replacement, and it now spawns its worker as a **command** rather than as an argument to node. The
test fixture that stands in for an older worker became executable for the same reason — a fixture
may be JavaScript, but it has to start the way the shipped one starts.

## How the port is judged now that the other side is gone

Both comparisons became frozen records at this commit, the discipline F148, F172, F178 and F184 all
arrived at:

- `red/red-mcp/src/tools.json` — the surface the JS worker answered with. `red-mcp.test.mjs`
  compares the running binary against it.
- `orchestrator/tests/mcp-conversation.json` — **56 answers**, the JS worker's own, captured from it
  immediately before deletion. `red-mcp-calls.test.mjs` replays the conversation against red-mcp and
  compares every answer.

And six suites that used to drive `mcp-worker.mjs` directly now drive the binary: `project-token`,
`task-writes`, `agent-identity`, `recordings`, `report-session` and `conversation-identity`. They
are the strongest evidence in this row — they were written against the JS worker's behaviour with no
thought for a port, and they pass unchanged.

## Sabotages

| Sabotage | Observed |
| --- | --- |
| the supervisor adopts a candidate without probing it | `Timed out: failed MCP candidate` — a connector that exits 3 is adopted |
| the probe insists on no particular tools | **passed, and that was the finding** |

The second one is why this row added a fixture. Emptying the probe's required list changed no test:
nothing fed the supervisor a candidate that *starts and answers* but cannot serve the update path.
`orchestrator/tests/incomplete-tool-worker.mjs` is that candidate now — it serves `workspace_info`
and `update_status` and no `update_workspace` — and the connector update is refused with
`update_workspace is missing` while the generation stays where it was. With the probe ignored, that
case goes red. A check nobody could break was a check nobody was making.

## Two parity defects the cutover found

- **202 is a success.** `update-workspace` answers **202 Accepted** with the job it queued; the
  shared HTTP client accepted only 200, so a queued update came back as a failure. `fetch`'s
  `response.ok` — which the JS side checked — is the whole 2xx range, and so is this now.
- **A test that would have overwritten the binary.** `runtime.test.mjs` proves a broken candidate is
  refused by writing garbage over the connector path. With that path pointing at `red-mcp` it
  corrupted the binary instead. The test owns a shim now and never the artifact.

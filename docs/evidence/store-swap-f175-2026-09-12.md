## The three fights this slice was actually about (each with its red)

1. **A shared one-shot is a close-race.** The first stateless design (one spawn per call,
   registered as `latest`) died inside the worker: concurrent per-action preflights shared the
   store and its owner closed it mid-call → `red-store-serve exited (0).` as a phantom
   preflight error. One-shots became unregistered (never `latest`).
2. **Loop-retention has three shapes, and all of them bite.** A persistent scratch held the
   event loop open at process exit (test files hung at end); an unref'd child let the loop
   drain mid-RPC (`Promise resolution is still pending but the event loop has already
   resolved`, also on `open()`'s started await and on `close()`). The final discipline: refs
   held at construction until `started`, refs around every call's flight, refs during close,
   unref'd at idle — so any client is loop-neutral, a service reaps itself at process death,
   and `close()` is the explicit, idempotent clean shutdown (main.mjs's host close now calls
   it, fixing the leak of a service per host start).
3. **The sync surface was the API all along.** `root()`, `getDraft()`,
   `listConversations()` are synchronous in the JS store — pure state lookups. The client
   answers them from the snapshot every answer refreshes (exactly the JS store's shape), which
   is also why the awaited call sites continue to be correct.

Performance numbers that justify the final shape: 30 stateless calls in 11.8 ms (vs ~35
process spawns per dashboard request in the one-shot design); the suite back to 16.2 s from
>15 min at the worst of the saga.

## Notes for the later deletion slices (F173 and beyond)

- The channel client is loop-neutral: `unref` everywhere at idle, `ref` around flights and
  shutdowns. Copy this discipline into F151/F152's services from day one.
- Sync state lookups from the snapshot are not a cache convenience — they are the API
  contract. Check the JS module's sync/async surface before writing the client.
- A test file's close discipline is now real: anything that opens a WorkspaceStore either
  closes it or relies on loop-neutrality at process death; main.mjs's host close() calls
  `store.close()`.
- The frozen-corpus pattern (capture once, freeze, replay forever) is how a deleted module
  stays an honest witness after the deletion; regenerate only with intent.

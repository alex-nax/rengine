# F185 criterion 1 — red-mcp answers the calls (2026-09-13)

Spec 129, KI-100. F184 made the tool *surface* data; this is the other half of what a pane does
with it. F185's remaining criteria — the cutover and the deletion — are **not** met here and are
filed as F187 with the question they turn on.

## How parity is judged

One scripted conversation of **50 calls** covering all 38 tools runs against **both** servers, each
in its own workspace built from the same fixture, and every answer is compared. Two workspaces
because the calls have effects: a token claimed on one server is not free on the other, and a task
written twice is two rows.

Two workspaces mean two sets of minted values, so the comparison normalises exactly those: uuids,
64-hex versions and tokens, ISO timestamps, loopback ports, epoch milliseconds, process ids,
measured durations, contest seconds, the workspace's own directory, and the eight characters of a
conversation id that name a pane in its title. Nothing else. Field names, ordering, refusal
sentences, numbers, booleans and the shape of every answer all have to match, and the answers are
compared as the client receives them — including `content[0].text`, which is the answer stringified,
so **key order is part of the comparison**.

Most of the conversation is refusals, deliberately: an agent meets *"this workspace predates …"* and
*"you do not hold the token"* far more often than a happy path, and those sentences are the part of
a port most likely to be subtly wrong. It also runs against a **live session** (output tail,
ownership, stop) and, halfway through, **another agent takes the token** — because that is the only
way the identity headers change an answer.

## Four sabotages, each observed failing for its own reason

| Sabotage | Observed |
| --- | --- |
| the identity headers are never sent | seven calls differ — `reload_desktop`, `update_workspace`, `open_script`, `dashboard_capture`, `launch_game`, `token_status`, `token_contest` |
| tool calls resolve to the session host, never the root-bound worker | `workspace_info`, `show_session`, `reload_desktop`, `update_status` differ — the worker's capabilities are not the host's |
| the file excerpt starts one line late | both `read_file` excerpts differ |
| an unknown tool answers a JSON-RPC error instead of an isError result | `not_a_tool` — the client throws where the JS server answers |

The first one is the one worth keeping. Its first form passed: with the pane holding the token
itself, an anonymous caller is not gated at all and gets the same answers. It only fails once
**another agent holds the token**, which is what made the fixture wrong rather than the code right.

## Three things the port had to learn from the workspace rather than from the JS source

- **The worker, not the host.** Tool calls resolve the root-bound runtime worker per call and fall
  back to the session host. Getting this wrong does not fail — it silently answers from a workspace
  with fewer capabilities, and every token, task and feed call is refused *plausibly*.
- **Chunked bodies.** The shared HTTP client asked in HTTP/1.0 and read whole bodies, which is true
  of the session host and false of the worker: the worker **proxies** the host and copies its
  `Transfer-Encoding: chunked` header onto what it forwards. A client that had only ever spoken to
  the host worked perfectly until it was pointed at the worker.
- **The workspace's own words.** `request()` on the JS side throws `body.error`; the shared client
  had been reporting `the workspace answered 404 for /api/dashboard?…`. It now surfaces the route's
  own sentence — *"Unknown project root."* — which is what a person can act on. `red-link`'s own
  refusal spec was updated to the better message, with the reason recorded in the test.

## Key order is behaviour

`content[0].text` is the answer stringified, and `serde_json` sorts map keys by default while the
JS host emits them in insertion order — so the same data reached an agent as a different string.
red-mcp uses `preserve_order`, the same reason red-agents does (F172).

## What is left, and the question it turns on

F187 carries the cutover and the deletion. It is not a line of code away: `mcp.mjs` spawns the tool
worker named by `runtime.toolWorker`, and the supervisor's layered update **probes a candidate
worker** (`runtime/tools.mjs`) before adopting it. Both assume the tool layer is a JS file that can
be swapped at runtime. Once the connector is a compiled binary, "update the connector layer" needs
an answer — rebuild, or ship a binary, or drop the layer — and that is a decision about spec 065's
update contract rather than a port detail.

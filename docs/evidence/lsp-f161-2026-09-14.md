# F161 — the language-server client, in Rust

2026-09-14. `orchestrator/runtime/lsp.mjs` (260) is deleted; `red-lsp` holds the diagnostic half of
the Language Server Protocol, and `runtime/lsp-client.mjs` (112) is how a caller reaches it.

## Shape: a process per root, not a service of a directory

`red-store` and `red-token` are services of a state directory, because a store and a ledger outlive
the host that reads them. A language server does not: the JavaScript spawned one per root inside the
worker and they died with it, and a replaced worker started its own. So `red-lsp-serve` is the
**stdio** shape — one process per project root, spawned by the client, ending when its stdin closes.

Only the diagnostic half is here. Completion, hover and definition are the editor's features; the
diagnostics are what an agent and a person have to agree about, because the editor pane and
`mcp__ide__getDiagnostics` read one store.

## The record

`orchestrator/tests/lsp-corpus.json` — six cases driven against the fake server: a file matched to
its declared server and told its buffer, a change re-published, a file nothing declares, the
directory wildcard reaching a file directly inside the directory, a server that is not on this
machine, a crash, and a close. Stable across three runs despite being timing-shaped.

Two things are folded because they are a machine's rather than a rule's: the temporary path and the
errno a spawn failure quotes. **The restart wait is not folded** — the first backoff is 500 ms by
rule, and a port that restarted eagerly would hammer a crashing server.

Three sabotages, each observed failing for its own reason and restored:

| sabotage | result |
|---|---|
| a crashed server's diagnostics outlive it | red |
| a crashing server restarts at once rather than backing off | red |
| a single star crosses a directory boundary | red, at the glob's own unit test |

## Three defects, none of which a corpus could have caught

**A Rust temporary-lifetime trap deadlocked every call.** The thread that waits for a server to exit
began `let status = { live.lock().child.take() }.map(|mut child| child.wait());`. That block looks
like it releases the lock; it does not — the guard is a temporary of the enclosing *statement*, so
it was held across `wait()`, which for a working server is forever. Every other call then blocked,
and the symptom was an `initialize` that was never even sent. Found by probing, not by the oracle:
a deadlock is not a wrong answer.

**The client's child was unref'd, so the loop drained mid-call.** Then, with the refs counted, the
unconditional unref after startup stole the handles from a `declare` already in flight. Both are the
discipline `store-client` wrote down: the refs are COUNTED, and the count covers startup.

**`stop()` released its refs and then waited for an exit.** Nothing was left keeping the loop alive,
so the await never settled — the same guard `store-client.close()` carries, for the same reason.

The debris those bugs left is worth naming too: a deadlocked `red-lsp-serve` never returns to read
its stdin, so it does not notice the EOF that is supposed to end it. Fourteen were left behind
during debugging. After the fix, a full suite run leaves zero.

## What changed around it

- `worker.mjs`'s diagnostics route asks **once** rather than reading a version and then the items:
  a version drawn before the publish a poller is waiting for is a poller told "unchanged" about a
  change. One call, and the version it answers is current.
- The IDE bridge's `getDiagnostics` awaits, because the servers answer over a socket now.
- `fake-language-server.mjs` carries its own framer: a test double that imported the implementation
  would be testing it against itself.
- `lsp.test.mjs` is retired — its framer case is a Rust unit test and its five behaviours are the
  corpus, driven now against both the client and the binary.
